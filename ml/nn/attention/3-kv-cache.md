# KV Cache и его сжатие

## Что такое KV cache и почему он дорогой

При авторегрессивной генерации трансформер вычисляет $K$ и $V$ для каждого нового токена, но уже вычисленные $K, V$ предыдущих токенов нужны снова на каждом следующем шаге. Их повторно не пересчитывают — кэшируют.

**Размер KV cache** на один слой:

$$\text{size} = 2 \times n_{\text{heads}} \times d_{\text{head}} \times L \times \text{dtype}$$

где $L$ — текущая длина контекста. При длинном контексте ($L = 128\text{k}$) это доминирующая часть памяти GPU.

Пример для Llama-3-70B: 80 слоёв × 8 KV-голов × $d_{\text{head}}=128$ × длина × 2 байта ≈ **160 GB** при 128k токенах — не влезает на один A100.

## Прогрессия архитектур: MHA → GQA → MQA → MLA

*GQA — Ainslie et al., 2023; Attention comparison and MLA — DeepSeek-V2, 2024*

Все четыре варианта кэшируют разное. Диаграмма из слайда (Cached During Inference — штриховка):

```
MHA           GQA           MQA           MLA
V V V V V V   V   V   V     V             V V V V V (реконструкция)
K K K K K K   K   K   K     K                  ↑
Q Q Q Q Q Q   Q Q Q Q Q Q   Q Q Q Q Q Q   c_t^KV  ← кэшируется
              (группы)
```

### Multi-Head Attention (MHA)

Каждая голова имеет **свои** $W_K^{(h)}, W_V^{(h)}$. Кэшируются все $n_h$ пар $(K^{(h)}, V^{(h)})$.

$$\text{Cache size} \propto 2 \times n_h \times d_h \times L$$

### Grouped Query Attention (GQA)

$n_h$ голов Q делятся на $g$ групп, каждая группа разделяет одну пару $(K, V)$. Кэшируется $g \ll n_h$ пар.

$$\text{Cache size} \propto 2 \times g \times d_h \times L$$

Используется в Llama 2/3, Mistral, Gemma. При $g = n_h$ — MHA, при $g = 1$ — MQA.

### Multi-Query Attention (MQA)

Все головы Q разделяют **одну** пару $(K, V)$. Минимальный кэш.

$$\text{Cache size} \propto 2 \times d_h \times L$$

Качество немного ниже MHA; используется для быстрого инференса.

### Multi-Head Latent Attention (MLA)

*DeepSeek-V2, 2024*

Вместо пар $(K^{(h)}, V^{(h)})$ кэшируется **один сжатый латентный вектор** $c_t^{KV}$, из которого при необходимости восстанавливаются все головы:

$$c_t^{KV} = W_D^{KV}\, z_t$$

$$k_t^{(h)} = W_{UK}^{(h)}\, c_t^{KV}, \qquad v_t^{(h)} = W_{UV}^{(h)}\, c_t^{KV}$$

Новые переменные: $c_t^{KV}$ — кэшируемый латент (размерность $d_c \ll n_h \cdot d_h$); $W_D^{KV}$ — матрица сжатия (down-projection); $W_{UK}^{(h)}, W_{UV}^{(h)}$ — матрицы восстановления (up-projection) для каждой головы.

$$\text{Cache size} \propto d_c \times L, \quad d_c \ll 2 n_h d_h$$

Ключевая идея: кэшируем только $c_t^{KV}$, а дорогие проекции $W_{UK}^{(h)}, W_{UV}^{(h)}$ применяются на лету. При этом число параметров не уменьшается — экономится только **память кэша**, не вычисления.

**Сравнение размеров кэша** (один слой, $n_h = 128$, $d_h = 128$):

| Метод | Кэш на токен |
|---|---|
| MHA | $2 \times 128 \times 128 = 32{,}768$ чисел |
| GQA ($g=8$) | $2 \times 8 \times 128 = 2{,}048$ чисел |
| MQA | $2 \times 128 = 256$ чисел |
| MLA ($d_c = 512$) | $512$ чисел |

## Другие техники управления KV cache

### KV Cache Eviction (вытеснение)

При длинных контекстах часть прошлых токенов можно удалить из кэша, оставив только «важные».

**H2O (Heavy Hitter Oracle)**: наблюдение — небольшое число токенов («heavy hitters») аккумулирует большую долю суммарного веса внимания. Политика: всегда держать в кэше initial tokens (первые несколько) + текущие heavy hitters по накопленному $\sum_t \alpha_{ti}$.

**StreamingLLM**: держим только начальные «sink tokens» (первые 4) + скользящее окно последних $w$ токенов. Первые токены важны потому, что softmax распределяет на них избыточный вес при длинных контекстах (артефакт нормировки). Позволяет работать с бесконечным контекстом при $O(w)$ памяти.

### KV Cache Quantization

Квантизация кэша до INT8 или INT4 снижает размер в 2–4 раза без пересчёта. Ключи и значения по статистике имеют «выбросы» (outliers) — нужны специальные схемы квантизации (per-channel, group quantization).

### Paged Attention (vLLM)

Вдохновлено виртуальной памятью ОС. KV cache разбивается на физические блоки фиксированного размера; логические последовательности отображаются на физические блоки через таблицу страниц. Позволяет:
- Эффективно батчировать запросы с разной длиной без паддинга.
- Разделять физические блоки между запросами (prefix sharing).
- Динамически выделять память без фрагментации.

## Сводная таблица

| Метод | Что кэшируется | Размер кэша | Качество |
|---|---|---|---|
| MHA | Все $K^{(h)}, V^{(h)}$ | $O(n_h \cdot d_h \cdot L)$ | Максимальное |
| GQA | Групповые $K, V$ | $O(g \cdot d_h \cdot L)$ | Почти как MHA |
| MQA | Одна пара $K, V$ | $O(d_h \cdot L)$ | Немного хуже |
| MLA | Латент $c^{KV}$ | $O(d_c \cdot L)$, $d_c \ll n_h d_h$ | Сравнимо с MHA |
| Eviction (H2O) | Топ-K важных + init | $O(K \cdot L)$ | Деградирует |
| StreamingLLM | Init + окно | $O(w)$ | Ограниченный контекст |
| Paged Attention | Блоки любого метода | То же | Не меняет |
